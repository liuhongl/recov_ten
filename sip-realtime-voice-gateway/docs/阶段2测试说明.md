# 阶段 2 测试说明：FreeSWITCH 媒体闭环

## 背景

阶段 2 的目标不是接入实时大模型，而是先验证新项目能否直接承接 FreeSWITCH 转出的电话媒体流。

从第一性原理看，电话智能客服链路最底层必须先满足一个条件：电话侧音频能够稳定进入网关，网关也能把音频稳定送回电话侧。这个条件不成立时，后面的 ASR、LLM、TTS 或端到端实时模型都无法可靠验证。

## 当前链路

```text
MicroSIP
  -> FreeSWITCH 9199
  -> mod_audio_stream
  -> ws://host.docker.internal:9101/media/fs/fs_stage5a_local
  -> sip-realtime-voice-gateway
  -> 原样回送 PCM
  -> FreeSWITCH
  -> MicroSIP 播放回声
```

## 数据格式

第二阶段只处理 FreeSWITCH 已经解码后的裸 PCM：

```text
encoding = pcm_s16le
sample_rate = 8000
channels = 1
frame_duration_ms = 20
frame_bytes = 320
transport = WebSocket binary frame
```

网关收到二进制帧后会立即原样写回同一个 WebSocket 连接。此阶段不做 PCMA 编解码，不做重采样，不接实时模型。

## 启动方式

```powershell
cd <repo>\sip-realtime-voice-gateway
python -m app.main --config configs/local.example.toml
```

服务会同时启动：

```text
HTTP health: http://127.0.0.1:9100/health
Media echo:  ws://0.0.0.0:9101/media/fs/{call_id}
```

当前本地 `ten_agent_dev` 容器会占用宿主机 `9000` 端口映射，所以阶段 2 默认使用 `9101`。本地 FreeSWITCH 的 `9199` 分机需要指向：

```text
ws://host.docker.internal:9101/media/fs/fs_stage5a_local
```

如果后续要切回 TEN 旧链路，再把 9199 指回旧 Media Hub 的 `9000` 端口。

## 自动化测试

```powershell
cd <repo>\sip-realtime-voice-gateway
python -m pytest
python -m py_compile app/config.py app/health_server.py app/logging_config.py app/main.py app/freeswitch_media.py
python -m app.main --config configs/local.example.toml --check-config
```

自动化测试覆盖：

- HTTP 健康检查。
- 配置读取和环境变量覆盖。
- WebSocket `/media/fs/{call_id}` 二进制音频回声。
- WebSocket 控制消息 `ping -> pong`。
- 非法媒体路径拒绝。

## 人工验收

1. 确认 Docker Desktop 和 FreeSWITCH 容器已启动。
2. 确认旧的 Media Hub 没有占用 `9000` 端口。
3. 启动 `sip-realtime-voice-gateway`。
4. 用 MicroSIP 拨打 `9199`。
5. 对着麦克风说话。
6. 能听到自己的回声，则阶段 2 的本地电话媒体闭环通过。

## 通过标准

必须同时满足：

- 网关日志出现 `freeswitch_media_connected`。
- 用户说话后日志出现 `first_freeswitch_audio`。
- 稳定收到并回送约 `320 bytes` 的音频帧。
- 电话端能听到自己的回声。
- 挂断后日志出现 `freeswitch_media_session_finished`。

## 还不能证明什么

阶段 2 只能证明 FreeSWITCH 到新网关的媒体闭环可用，不能证明：

- 实时模型连接可用。
- 端到端智能回复延迟达标。
- PCMA 与模型侧 PCM 的重采样已经正确。
- 用户打断能力已经具备。
- 真实 SIP Trunk 上线无风险。

这些内容需要在后续阶段分别验证。
