# 阶段 6 测试说明：持久会话与完整打断控制

## 背景

阶段 5 已经证明电话实时链路能跑通：

```text
MicroSIP -> FreeSWITCH -> Gateway -> Qwen-Omni-Realtime -> Gateway -> FreeSWITCH -> MicroSIP
```

但阶段 5 的实现本质仍偏“轮次式”：

- 用户说完后才把整段音频提交给模型。
- 每轮模型调用边界比较粗。
- 打断主要靠清空本地播放队列。
- 旧轮次迟到音频没有完整的 `turn_id` 隔离模型。

阶段 6 的目标是把这条链路升级为更接近真实电话智能客服需要的状态机：

```mermaid
flowchart LR
  A["通话接通"] --> B["建立持久 realtime WebSocket"]
  B --> C["用户说话时持续 append 16k PCM"]
  C --> D["本地 VAD 判定一句话结束"]
  D --> E["commit + response.create"]
  E --> F["response.audio.delta 流式播放"]
  F --> G["用户开口打断"]
  G --> H["response.cancel + 清空播放队列 + turn_id 失效"]
```

## 当前实现范围

本阶段已实现：

- `RealtimeStreamingSession`
  - 每通电话建立一个持久 Realtime WebSocket。
  - 通话内多轮复用同一个连接，不再每轮重新连接模型。
  - 支持持续发送 `input_audio_buffer.append`。
  - 支持 `input_audio_buffer.commit` + `response.create`。
  - 支持 `response.cancel`。
  - 支持 `input_audio_buffer.clear`。
  - 将 `response.audio.delta` 以 `turn_id` 回调给电话网关。

- 电话网关状态机
  - VAD 检测到用户开始说话时创建新的 `turn_id`。
  - 用户说话过程中持续把 `8k PCM` 重采样成 `16k PCM` 并 append 给模型。
  - VAD 判定结束后才 commit 并创建 response。
  - 模型返回的音频帧进入带 `turn_id` 的播放队列。
  - 当前有效 `turn_id` 之外的迟到音频会被丢弃。
  - 用户在 AI 播放或生成中开口时：
    - 清空本地播放队列。
    - 将当前输出 `turn_id` 置失效。
    - 如果模型仍在生成，发送 `response.cancel`。
    - 清空模型输入缓冲，准备新一轮输入。

- 延迟调整
  - 默认 `end_silence_ms` 从 `800ms` 降到 `500ms`。
  - 这能减少用户停顿后的本地等待时间，但如果用户说话中间停顿较长，可能更容易提前切句。

- 本地回声护栏
  - 默认 `barge_in_enabled = false`。
  - MicroSIP 本地测试如果使用外放，AI 播放音频可能被麦克风回采，网关会把 AI 自己的声音误判成用户插话。
  - 默认关闭后，AI 播放期间的疑似插话会被忽略，优先保证不混播、不自触发。
  - 使用耳机、具备回声消除的真实电话或后续接入 AEC 后，可以设置 `VAD_BARGE_IN_ENABLED=true` 再验证完整打断。

## 数据格式

上行：

```text

```

下行：

```text
Realtime -> Gateway: 24kHz / mono / pcm_s16le / base64 delta
Gateway -> FreeSWITCH: 8kHz / mono / pcm_s16le / 20ms / 320 bytes
```

覆盖点：

- 持久 Realtime session 可以在单个 WebSocket 连接内完成多轮 turn。
- 每轮只发送一次 `session.update`，但可以发送多次 append/commit/response.create。
- 电话网关能把模拟模型的 `24k PCM` 转成 `8k / 20ms / 320 bytes` 播回客户端。
- 播放中插话会清空本地播放队列。
- 旧 turn 的音频帧不会继续被当成新 turn 播放。

## 2026-05-09 第一次人工复测结果

现象：

- 声音断断续续。
- 第一次 AI 回复回答到一半后，像是在第二次回答中继续出现。

日志关键点：

```text
turns_started=3
turns_committed=3
turns_completed=3
turns_failed=0
interruptions=1
dropped_playback_frames=106
dropped_stale_frames=0
```

第二轮输入转写为：

```text
input_transcript=您好。
```

分析：

- `dropped_stale_frames=0` 说明服务器侧没有把旧 `turn_id` 的迟到音频误播到新 turn。
- 第二轮识别到的“您好”与第一轮 AI 回复开头一致，更像是本地软电话外放被麦克风回采，导致网关把 AI 自己的声音当成用户插话。
- `dropped_playback_frames=106` 说明第一次回复被误触发的打断清掉了约 `2.12s` 的剩余播放，因此主观上会听到“第一轮说到一半断掉”。

修正：

- 默认关闭播放中 barge-in：`barge_in_enabled = false`。
- 当前本地测试优先验证多轮稳定和不混播。
- 完整打断需要在耳机、真实电话回声消除或服务端 AEC 方案下继续验证。

## 当前限制

- 本阶段已经证明：在本地 VAD / Manual mode 上继续补丁式优化，不适合作为商用电话智能客服主线。后续转向阿里 Server VAD 路线，详见 `阿里ServerVAD商用路径说明.md`。
- 打断时仍是本地硬清播放队列，尚未做淡出，所以尾音可能仍会突兀。
- `response.cancel` 已发送，但不同模型服务端对已生成音频的取消时机可能不同，所以仍必须依赖本地 `turn_id` 丢弃迟到音频。
- 当前没有业务工具，事实类问题仍可能幻觉。例如日期、订单、账户状态不能靠模型裸答。
- 当前没有回声消除。默认关闭 barge-in 可以避免本地软电话外放自触发，但这也意味着 AI 播放期间用户插话会先被忽略。
