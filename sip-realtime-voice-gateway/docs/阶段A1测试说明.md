# 阶段 A1 测试说明：阿里 Server VAD 离线事件流验证

## 1. 背景

阶段 6 的本地 VAD / Manual mode 链路已经能跑通电话模型闭环，但在商用电话场景里暴露出两个根本问题：

- 本地 VAD 负责断句，模型只在本地提交后才开始生成，turn-taking 不够自然。
- 本地软电话外放测试容易把 AI 播放声回采成用户输入，导致打断和多轮状态变乱。

因此后续主线切换为阿里 Qwen-Omni-Realtime 的 Server VAD：Gateway 只持续发送用户音频，用户开始、结束、提交和响应生成由服务端事件驱动。

阶段 A1 不接电话、不改 FreeSWITCH 热链路，只验证当前账号、模型、音频格式和事件流是否可用。

## 2. 当前实现

新增命令：

```powershell
python -m app.server_vad_probe
```

核心实现位置：

- `app/server_vad_probe.py`：离线探针入口，支持 `--input-pcm` 和 `--input-wav`。
- `app/realtime_client.py`：新增 `run_server_vad_probe`，负责 WebSocket 连接、Server VAD session 配置、事件收集和音频输出。

当前探针行为：

- `session.update` 中设置 `turn_detection.type = "server_vad"`。
- 音频以 `input_audio_buffer.append` 持续发送，不手动发送 `input_audio_buffer.commit`。
- 不手动发送 `response.create`，由服务端在 VAD 判停后触发。
- 探针按实时节奏发送音频，默认 `chunk_ms = 100`、`send_delay_ms = 100`。
- 探针边发送边读取服务端事件。
- 离线单轮测试中，一旦收到 `input_audio_buffer.speech_stopped`，停止继续灌入后续离线音频，避免一个测试文件被误当成连续多轮输入。

  --timeout 90

```powershell

  --env-file ../ai_agents/.env `

  --silence-duration-ms 2000 `
  --trailing-silence-ms 3000
```

## 5. 结论

阶段 A1 验证通过：

- 当前 DashScope Key、模型和音色可用于 Server VAD 链路。
- 服务端可以返回 `speech_started`、`speech_stopped`、`committed`、`response.created`、`response.audio.delta`、`response.done`。
- Gateway 可以保存服务端事件、转写文本、`response_id` 和模型输出音频。
- 离线探针已经改为边发边读，更接近真实实时链路。

进入 A2 前必须注意：

- Server VAD 的 `silence_duration_ms` 需要做成电话链路配置项。
- 800ms 更利于低延迟，但对长句、朗读、停顿多的音频有截断风险。
- 2000ms 更稳，但会显著增加用户说完到 AI 开始回复的等待时间。
- A2 应先以电话短问答为主测样本，再逐步加入长句、噪声、停顿和插话样本。
